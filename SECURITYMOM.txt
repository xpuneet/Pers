Meeting notes:

•	Systems Integration Framework Scope: Joycell explained that the eight-week engagement will produce a Chaucer-specific Systems Integration Framework (SIF), reference architecture, integration pattern catalogue and governance guidance, with the SIF developed first and the APIM high-level design beginning in week four. 
o	Framework Purpose: Joycell stated that Chaucer currently has different integration designs and applications but no single framework governing delivery teams, architecture and suppliers. The SIF will provide a common direction and include a reference architecture covering the main Azure Integration Services components, including existing services such as Logic Apps and Service Bus and other components that may be needed in future.
o	Integration Patterns: In response to Chad's question, Joycell confirmed that the pattern catalogue will define approved patterns across synchronous data exchange, asynchronous messaging, asynchronous events, webhooks and notifications, and cross-system process orchestration. Existing Logic Apps and Service Bus usage will be reflected, while Event Hubs will remain an available option for suitable streaming use cases.
o	Governance Guidance: The framework is intended to provide actionable decision guidance, guardrails and exception handling rather than implement working integrations or redefine Chaucer's cloud strategy. The team will document which pattern, and Azure component should be used for common scenarios and capture the rationale so delivery teams and suppliers can apply the guidance consistently.
o	Delivery Timeline: The plan covers eight weeks: mobilisation and discovery in week one, development of the SIF core through the early weeks, APIM high-level design beginning around week four, joint review, and finalisation for TDA submission. Implementation, provisioning and deployment are future-phase activities rather than part of this engagement.

•	Security Governance and Public API Exposure: Chad challenged the proposed public API capability, explaining that private endpoints and private links are the preferred position and that any public exposure must be treated as an exception with defined controls, security approval and risk acceptance. 
o	Public Exposure Position: Chad said that publicly exposing APIs would not normally be accepted from a security perspective, even where an Azure Web Application Firewall is placed in front, because the endpoint remains publicly reachable. Private endpoints and private links should be preferred; any unavoidable public exposure must have a significant business need and an explicitly accepted risk.
o	Exception Approval: Chad recommended that sensitive patterns, particularly public API patterns, list mandatory prerequisites and require approval before engineering begins. Joycell confirmed that the SIF will include this guidance. Chad clarified that TDA alone should not approve the exception: security approval or escalation to the risk register and senior leadership is required where the risk affects the wider security posture.
o	Security Review Gates: Chad distinguished between standard private patterns and exceptions. Approximately most standard patterns should proceed through an agreed security baseline without significant additional gates, while patterns that cannot meet the baseline must trigger the exception process. The SIF should identify the red lines, required controls and point at which security review is mandatory.
o	APIM Security Design: Joycell asked whether APIM could be publicly exposed behind an Azure application gateway or WAF. Chad answered that this would still constitute public exposure and might not provide the required security depth. If APIM has an external use case, the design should consider a properly secured, enterprise-grade reverse-proxy or managed security service, with the associated costs and controls identified during the APIM phase.

•	Security Architecture and Technology Selection: The group agreed that security requirements should drive the eventual gateway and protection technology, rather than assuming Azure-native services, with costs, DDoS protection, logging, risk and commercial benefit assessed before a decision is made. 
o	Technology-Neutral Requirements: Joycell noted that the current work is Azure-focused and that the original requirements refer to Azure tools. Chad advised that the SIF and APIM material should state the required security outcomes, while the final product or service selection remains subject to agreement between the relevant architecture, security, network and business stakeholders.
o	Enterprise Security Options: Chad explained that an Azure-native application gateway may not provide the same protection, reporting, filtering and zero-day detection as a specialist security appliance or managed service. A reverse-proxy design could expose a managed front end while keeping the Chaucer API privately connected at the back end, but this would introduce additional cost and require a fuller security architecture assessment.
o	Budget And Risk: The team must quantify the costs of gateways, DDoS protection, ingress and egress, supporting services and any third-party security platform. Chad said that security architecture should identify and quantify residual risks rather than accept them on behalf of the organisation; decisions on funding and whether the commercial benefit justifies the cost should be taken by the appropriate business and senior stakeholders.

•	Identity Secrets and Certificate Management: Chad recommended continued use of managed identity and OAuth 2.0 wherever possible, while the team investigates stronger integration between Azure Key Vault, CyberArk or another privileged-access solution for static secrets, key rotation and certificates. 
o	Authentication Standards: Chad said the preferred direction is OAuth 2.0 using client credentials or authorisation codes, with managed identities used for service-to-service authentication wherever possible. Existing external integration examples use managed identity and Entra application registrations with modern authentication and short-lived tokens.
o	Privileged Secrets: For keys, credentials and other static secrets that cannot use managed identity, Chad recommended centralised storage and controlled access through a privileged-access management capability. CyberArk is the current incumbent, but its use should be assessed beyond simple vaulting so that applications can retrieve or reference secrets without copying them into insecure locations.
o	CyberArk Roadmap: Chad said the migration of CyberArk from on-premises hosting to software as a service is nearing completion but was primarily a lift-and-shift. A broader discovery and modernisation exercise is expected next year, with possible consideration of CyberArk's additional capabilities or alternative products over a longer horizon. Further requirements gathering will involve security, DevSecOps, infrastructure-as-code, engineering and integration teams.
o	Latency And Certificates: Joycell highlighted that Azure-native Key Vault and managed identity currently provide low-latency retrieval. Chad agreed that any PAM-based approach must preserve acceptable performance and suggested an interim model in which CyberArk manages rotation and policy while applications continue to retrieve values through Key Vault. CyberArk can store certificates and potentially replicate them to Key Vault, but certificate generation remains an item for further investigation.

•	Network Isolation and Access Control: The discussion identified east-west traffic, private endpoints, NSGs and least-privilege RBAC as design dependencies that must align with the evolving UK South network model and be assessed per service or API. 
o	East-West Traffic: Chad explained that UK South services will increasingly operate behind multiple controls, including NSGs and Palo Alto firewalls, as the modernised environment adopts stronger zero-trust and segmentation principles. The required routing and access will depend on the specific service, API and back-end data source.
o	Network Dependencies: The infrastructure and network architecture teams agreed to provide their views on Azure South inbound and outbound routing. The SIF should account for future migration and modernisation so that integration patterns remain compatible with changes to routing, segmentation, firewall rules and back-end service locations.
o	RBAC Process: Joycell said current solution designs specify the RBAC permissions needed by components such as Logic Apps and Service Bus. Chad confirmed that security and cloud operations will assess whether each request follows least privilege, with higher-risk permissions subject to peer review and service-by-service evaluation. The cloud operations team is expected to enforce RBAC through privileged identity management for groups, with exceptions for APIs, managed identities or other authentication constraints.
o	Reusable Permissions: Chad proposed defining pre-reviewed permission sets for recurring integration use cases. Where a later solution repeats an already approved design and retains the same front-end and back-end pattern, the previous TDA approval should be reusable as a recognised pattern rather than requiring a wholly new assessment.

•	External Party Authentication: The group agreed that any future external access should use modern authentication, managed identities or Entra application registrations where appropriate, with key ownership, rotation and private connectivity explicitly addressed in the SIF. 
o	External Access Model: Joycell described a likely model in which external applications use Entra application registrations and token acquisition to access APIs, while internal services such as Service Bus and Logic Apps remain private unless deliberately exposed through an API layer. Chad said existing data integrations generally use managed identities, application registrations, modern authentication and short-lived tokens.
o	Key Management: Chad said that any external-party scenario must define who manages private keys, how keys are rotated and how authentication is exposed. Key Vault may be usable, but a dedicated key-management or PAM solution may be preferable depending on the final requirements.
o	SIF Coverage: The team agreed that these external authentication patterns should be documented in the SIF, including the preferred modern approach and the treatment of less-preferred mechanisms such as long-lived SAS tokens. Chad noted that SAS-based requests had previously been pushed towards the risk register where they could not be avoided.

•	Monitoring Logging and Observability: Joycell described the current Azure-native monitoring model, while Chad requested validation that relevant security logs reach CrowdStrike and that any future gateways or APIM components integrate with Group Security monitoring. 
o	Current Monitoring: Joycell said the integration team uses Application Insights, sends data to Log Analytics, and operates dashboards and Azure alerts for operations and issue resolution. This is the current baseline for integration observability.
o	Security Log Ingestion: Chad said Azure logs already cover areas such as Key Vault activity, integration CI/CD deployments and Azure administrative events. The team must verify that relevant security events are being ingested by CrowdStrike and engage Graham's Group Security team to confirm what it can receive and what additional integration options are available.
o	Future Components: Any newly introduced gateway, load balancer or APIM security service must be assessed for security-event capture and forwarding to CrowdStrike. Chad also distinguished LogicMonitor, which is intended mainly for performance and operational monitoring, from security monitoring; ownership and onboarding arrangements should be confirmed with the relevant service owners.
o	Event Hub Usage: Chad identified an existing Event Hub pattern used by Security to stream Azure, Key Vault, storage and security logs to CrowdStrike. Joycell will consider this existing infrastructure and infrastructure-as-code pattern when documenting Event Hub as a possible SIF component.

•	Standards Stakeholder Collaboration: Joycell and Chad agreed to use existing enterprise, integration and cloud-security policies as inputs, share the live SIF early, involve the data and security stakeholders, and hold a further review session once draft artefacts are available. 
o	Policy Alignment: Chad asked the team to compare proposed patterns with existing integration and engineering standards, the cloud security framework and Azure policies. He offered to provide the cloud security framework and related documentation, noting that Azure policies may restrict public endpoints or require exceptions and are expected to be enforced through cloud operations with security oversight.
o	Security Standards Ownership: Existing architecture standards contain some security material, but there may be a need for more specific integration security patterns and minimum standards. Chad said responsibility for wider security policy review may sit with Stuart Baker or his quality and technical assurance function, while topic-specific integration guidance could be developed collaboratively from concrete use cases.
o	Data Team Boundary: The boundary between the SIF and the data team's ETL, ELT, Snowflake and other data flows is not yet defined. A session with the data team is scheduled for the following Tuesday to determine which data capabilities belong in the framework and which remain under data-team control.
o	Ongoing Review: Joycell proposed preparing draft content and holding a further session around week 3. Chad and the wider stakeholder group agreed that the document should be shared as a live artefact for continuous feedback rather than circulated only immediately before TDA, with additional engagement involving Kevin, Graham, identity stakeholders and other relevant teams as the design becomes more concrete.
